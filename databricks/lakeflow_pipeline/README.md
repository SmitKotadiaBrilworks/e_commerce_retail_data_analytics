# Elecmart Medallion Pipeline — Lakeflow Declarative Pipeline

A second, independent path to the same silver + gold layer as `databricks/notebooks/`, built as a
**Lakeflow Declarative Pipeline** (formerly DLT) instead of a Databricks Job. Demonstrates
Lakeflow's data-quality expectations (`@dp.expect_or_fail`, `@dp.expect`) and materialized-view
dependency graph.

Deployed in the workspace as pipeline **"Elecmart Medallion Pipeline (Bronze → Silver → Gold)"**.
These files are a backup/reference copy of that pipeline's source (`transformations/silver/`,
`transformations/gold/` in the pipeline's workspace root) — editing them here does **not** update
the live pipeline; re-upload via `databricks workspace import <path> --file <file> --format RAW
--overwrite` or push through a bundle.

## What it does

- Reads from `elecmart.bronze.*` (populated by the Job's `01_bronze` task — this pipeline has no
  bronze layer of its own)
- `silver/silver_dimensions.py`, `silver/silver_facts.py` — cleans bronze into `elecmart.silver.silver_*`
  materialized views, with data-quality expectations on every table
- `gold/gold_dimensions.py`, `gold/gold_facts.py` — enriches silver into `elecmart.gold.gold_*`
  (joins, allocated discount / net revenue / profit calc on `gold_fact_sale`)
- `gold/bi_tables.py` — 25 `elecmart.gold.bi_*` BI marts, same shape as `notebooks/04_gold_bi_marts.sql`
  (this is what the AI/BI dashboard reads)

## Table ownership — pick one path, not both

This pipeline and the Job in `databricks/notebooks/` both want to own `elecmart.silver.*` and
`elecmart.gold.*`. A Lakeflow pipeline can't take over a table that already exists as a plain
(non-pipeline-managed) table, and vice versa. Once this pipeline owns those tables:

- **Don't re-run** `notebooks/02_silver.sql`, `03_gold_star.sql`, `04_gold_bi_marts.sql` — they'll
  recreate the tables as plain Delta tables and the next pipeline update will fail with `a MANAGED
  table already exists with that name`.
- `notebooks/01_bronze.sql` (and `00_setup.sql`) are still needed — this pipeline reads from bronze
  but doesn't populate it.
- To switch back to the Job owning silver/gold, drop the pipeline-owned tables first (or point this
  pipeline at different schema names).

## Fixes applied to get it running

The pipeline as originally generated by the Databricks Assistant had three bugs:

1. **Duplicate table definitions** — the assistant generated the silver/gold logic twice under
   different filenames (`dimensions.py`/`facts.py` **and** `silver_dimensions.py`/`silver_facts.py`,
   same for gold), so every table was declared twice → `Found duplicate table
   'elecmart.silver.silver_fact_sale'`. Fixed by deleting the newer, plainer duplicates and keeping
   the versions with expectations (these files).
2. **Ambiguous column** — `gold_dim_product()` joined `product` → `category` → `subcategory`, but
   `silver_dim_subcategory` itself carries a `category_id` column, so after the join there were two
   `category_id` columns. Fixed by dropping `category_id` from `subcategory` before the join
   (`gold/gold_dimensions.py`).
3. **`timestampNtz` Delta feature** — several source columns (`transaction_timestamp`,
   `session_start_time`, etc.) are inferred as `TIMESTAMP_NTZ` from the Parquet source, which
   Lakeflow Pipelines require enabling explicitly. Fixed by adding to the pipeline's `configuration`:
   `spark.databricks.delta.properties.defaults.feature.timestampNtz = supported`. Needed a
   full-refresh to apply to tables Lakeflow had already partially created before the fix.
